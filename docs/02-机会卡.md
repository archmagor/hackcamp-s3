## 机会卡 A（入口：新能力）

- 谁，在什么场景下：跑第三方 AI agent（购物、订阅、API 调用、DeFi 交易）的普通用户；agent 需要在无人监督下代表用户发起支付。
- 现在怎么做，哪一步最别扭：用户把钱包私钥或 session key 交给 agent，靠 prompt 约束 + 后端 policy（例如"单笔 < $10、每日 < $100"）限制；别扭在**约束位于 policy 层** —— agent 被 prompt injection、模型 hallucination、或后端被绕过时钱就没了，事后追溯只能看链上转账，看不到"人类究竟授权了什么、授权凭证是否已被消费"。
- 我改变哪一步：把"限额 / 一次性 / 收款方白名单"从 agent 后端 policy **下沉到支付凭证本身** —— 每次人类授权产出一张绑定 Concordium Verify and Access 证明 + Agent Registry badge 的**一次性支付凭证**，凭证必须在同一笔 x402 支付交易里被消耗，不能被存储、重放、转手（机制参照 ScalpLess 的 hot potato `Attested` struct，见 https://ethglobal.com/showcase/scalpless-15fnr）。
- 用到的新能力 / 赛事要求的技术：Concordium **Verify and Access**（一次性可验证凭证语义）+ **Agent Registry / Verified by Concordium badge**（把 agent 绑到人类身份）+ **x402 payments**（HTTP 层结算通道，凭证随支付请求传递）+ ERC-8004（EVM 侧 agent 注册，与 Concordium badge 交叉引用）。组件来源：`docs/01-选赛卡.md` "必需集成"字段；各组件的具体 API、以及 Verify and Access 是否原生支持"消耗语义" → **未确认**。
- 现有替代方案（附链接）：Coinbase **x402**（https://github.com/coinbase/x402 ，只做支付通道，不做授权凭证的一次性绑定）／ **Skyfire**（https://skyfire.xyz ，agent 支付钱包，policy 层限额）／ **Payman**（https://payman.ai ，agent 支付抽象层）／ **ERC-4337 paymaster + session key**（https://ethereum.org/en/roadmap/account-abstraction/ ，限额靠 paymaster 合约逻辑，非凭证级）／ **ScalpLess**（https://ethglobal.com/showcase/scalpless-15fnr ，Move abilities 层强制限价，机制参照物，仅在 Sui 上、仅做黄牛场景）。链接可访问性需在提交前复核。
- 为什么现在能做：Concordium Trusted Agents Hackathon 首次把 Verify and Access + Agent Registry + x402 三件套一起开放给外部 agent 集成（`docs/01-选赛卡.md` 原文引用："**Can I bring an agent that lives on another chain? — Yes, that is the point.**"）；x402 在 EVM 侧已有生产 SDK；ScalpLess 在 ETHGlobal Tokyo 2026 展示了"类型级约束 > policy 级约束"的可行性（**作者主张**，未独立验证）。
- 最危险的假设：ScalpLess 的类型级约束依赖 **Move-style object capabilities**（abilities 是类型的一部分、编译器强制）；Concordium 合约模型（CIS / Wasm）能否等价表达"无 store ability、必须同交易消耗"的对象语义 → **未确认**。若不能，凭证一次性只能靠后端签名 + nonce 检查，退化回 policy 层，本卡核心差异化消失。
- 2 小时内能做的验证动作：① 读 concordium-node-sdk-js（https://github.com/Concordium/concordium-node-sdk-js ）+ CIS 标准，确认合约能否表达"一次性消耗凭证"；② 从 Concordium testnet faucet 领 CCD（`docs/01-选赛卡.md` 已提到 "test CCD comes free from the testnet faucet"），跑通最小 Verify and Access 证明；③ 用 Coinbase x402 官方 demo 挂上 Concordium badge 头字段，验证支付请求能否携带凭证。
- 推翻条件（出现什么就放弃）：① Concordium 合约层无法表达类型级一次性约束、且 Verify and Access 只提供"是 / 否"验证而不提供"消耗"语义 → 与 Skyfire / Payman 无差异 → 放弃；② Agent Registry badge 只覆盖 agent 本身、不接受"人类 → agent 的一次性授权"子凭证 → 授权链断裂 → 放弃；③ 2 小时内三件套任一连不通 testnet（SDK 崩溃 / faucet 关闭 / x402 与 Concordium 头字段冲突）→ 时间预算不够 → 放弃。
